Camelot distribution (harmonic-mixing ready)

Most common codes across the catalog: 2A (22,909), 4A (12,263), 10A (11,727), 12A (11,286), 7A (10,170), 9A (9,965), 5B (8,643), 5A (7,578). A dark, minor-key, fast catalog — well suited to harmonic mixing.

What's missing — the mixing/compatibility engine GAP

The building blocks (Camelot + BPM + confidence per track) are computed, but nothing ties them into track-to-track "what can I mix next" decisions. These are specced (in PROPOSED_METADATA_FIELDS.md / FIELD_INVENTORY.md) but not built:

  • camelot_key — deterministic key+mode → Camelot map (e.g. A-minor → 8A). "The single most-requested DJ field."
  • harmonic_neighbors — for each track, the song ids mixable with it: same Camelot code, ±1 on the wheel, or relative major/minor, AND within a pitch-safe BPM window (±6%). Turns 165k tracks into a navigable "mix-into" graph. (Distinct from nearest_neighbors, which is timbral similarity, not harmonic compatibility.)
  • tempo_transition_class — mixable tempo bands including half/double-time (e.g. 140 BPM ↔ 70 BPM halftime).

How this connects to theDAW's DJ tab (our work)

  • theDAW already uses Camelot/key for display — a harmonic key-match chip and a client-side Camelot map (frontend/src/lib/camelot.ts).
  • The set-builder (backend/modules/library/suggester.py) already orders tracks by Camelot + a BPM-flow curve — so harmonic ordering exists on the build side.
  • But the live Auto-DJ we worked on plays a set in its given order and beatmatches/crossfades — it does not pick or reorder the next track by harmonic/tempo compatibility.

Bottom line: harmonic-mix ingredients (Camelot + BPM) are computed at full-library scale in SunoHarvester, and theDAW can already read them — but the harmonic_neighbors matching engine that would drive real "what mixes into what" decisions is specced, not built. That's the natural next build if you want compatibility-aware auto-mixing.
